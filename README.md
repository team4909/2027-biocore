# 2027-BioCore

FRC Team 4909's WPILib **2026** robot code for a CTRE Phoenix 6 swerve drivetrain with PathPlanner autonomous routines and PhotonVision AprilTag pose estimation.

> **Repo name vs. season:** the repository is called `2027-biocore`, but `build.gradle`, `settings.gradle`, and `.wpilib/wpilib_preferences.json` all target the **2026** season (GradleRIO 2026.2.1, Java 17). Treat it as a 2026 robot.

## Overview

This robot uses:

- **Swerve drive** with CTRE Phoenix 6 `SwerveDrivetrain` (4 TalonFX drive motors, 4 TalonFX steer motors, 4 CANcoders, 1 Pigeon 2).
- **PathPlanner** for path following and auto selection. Named commands are registered for scripted turns.
- **PhotonVision** with two cameras, `frontleftcamera` and `frontrightcamera`, feeding AprilTag pose estimates into the drivetrain's pose estimator.
- **CTRE HootAutoReplay** for timestamp/joystick replay and **SignalLogger** for drive-state logging.
- A simple `TimedRobot` loop (not AdvantageKit `LoggedRobot`); the command scheduler is run manually.

The autonomous chooser is PathPlanner-only through `AutoBuilder.buildAutoChooser()`.

## Architecture

```
Main
 └─ Robot (TimedRobot)
     ├─ HootAutoReplay (timestamp + joystick replay)
     ├─ CommandScheduler.run()
     └─ RobotContainer
         ├─ CommandSwerveDrivetrain (TunerConstants.createDrivetrain())
         ├─ Telemetry (SignalLogger + NetworkTables)
         ├─ Vision (registered as a subsystem)
         │   ├─ VisionIOPhotonVision(frontleftcamera)
         │   └─ VisionIOPhotonVision(frontrightcamera)
         │       (VisionIOPhotonVisionSim in simulation)
         ├─ AutoBuilder (PathPlanner)
         └─ Xbox controller bindings
```

### Drivetrain

`CommandSwerveDrivetrain` extends the Tuner X generated `TunerSwerveDrivetrain` and implements `Subsystem`. It adds:

- `getRobotRelativeSpeeds()` and `resetPose()` for PathPlanner.
- `applyRequest(...)` helper for `SwerveRequest`s.
- SysId routines.
- `addVisionMeasurement(...)` / `samplePoseAt(...)` overrides that convert FPGA timestamps into the Phoenix timebase.
- Operator-perspective handling for red/blue alliance (affects `FieldCentric` requests, not the raw pose).
- A 4 ms simulation notifier that calls `updateSimState(...)`.

### Vision

`Vision` is a `SubsystemBase` that every loop:

1. Calls `updateInputs()` on each camera IO.
2. Reads `PoseObservation`s and `tagIds`.
3. Rejects observations that have no tags, high ambiguity on single tags (`> 0.3`), unrealistic Z (`> 0.75 m`), or fall outside the field.
4. Computes standard deviations from average tag distance and tag count, scaled by `cameraStdDevFactors`.
5. Sends accepted poses to `drivetrain.addVisionMeasurement(pose, timestamp, stdDevs)`.
6. Publishes tag/robot poses to NetworkTables for AdvantageScope.

In simulation, `VisionIOPhotonVisionSim` registers both cameras with a shared `VisionSystemSim` so the simulated robot can see AprilTags.

## Autonomous / PathPlanner

- Autos and paths live in `src/main/deploy/pathplanner/` and are edited with the PathPlanner GUI, not by hand.
- `RobotConfig.fromGUISettings()` reads `deploy/pathplanner/settings.json`. If it is missing/malformed, `configureAutoBuilder()` logs an error and autos are unusable.
- Auto selection is via the SmartDashboard chooser **"Auto Mode"**.
- `shouldFlipPath` is driven by the SmartDashboard chooser **"Manual Mirror Override"**, defaulting to **"Don't Mirror (Blue)"**. Autos do **not** automatically flip for the red alliance unless that option is selected.
- Named commands registered before `configureAutoBuilder()`:
  - `Spin90` → `TurnToHeading(drivetrain, 90.0)`
  - `Spin180` → `TurnToHeading(drivetrain, 180.0)`

Current autos:

- `1 meter + 90 degrees`
- `90 degree auto`
- `180 degree auto`
- `Three Meter Auto`

### Path-following output

`RobotContainer.driveRobotRelative(ChassisSpeeds)` currently applies PathPlanner's **robot-relative** speeds through a `SwerveRequest.FieldCentric`. That request interprets the values as **field-relative**, which is incorrect whenever the robot has a nonzero heading. If path tracking is poor while rotated, switch that method to `SwerveRequest.ApplyRobotSpeeds` (or `RobotCentric` with the same velocities).

## Vision

### How it is wired

`RobotContainer` constructs `Vision` with the drivetrain's `addVisionMeasurement` as the consumer:

```java
private final Vision vision = new Vision(
    drivetrain::addVisionMeasurement,
    createCameraIO(VisionConstants.frontLeftCameraName, VisionConstants.robotToFrontLeftCamera),
    createCameraIO(VisionConstants.frontRightCameraName, VisionConstants.robotToFrontRightCamera)
);
```

`createCameraIO(...)` returns `VisionIOPhotonVisionSim` in simulation and `VisionIOPhotonVision` on the real robot. `Vision` is explicitly registered with `CommandScheduler` so its `periodic()` runs even though it has no commands.

### Camera configuration (coprocessor)

For vision to produce poses:

1. The two cameras must be named exactly `frontleftcamera` and `frontrightcamera`.
2. Each camera needs a pipeline with **AprilTag** detection and 3D solving enabled.
3. The field layout on the coprocessor must match WPILib's 2026 default field (`AprilTagFields.kDefaultField`).

### Robot-to-camera transforms

`VisionConstants.robotToFrontLeftCamera` and `robotToFrontRightCamera` define each camera's pose relative to the robot origin: **+X forward, +Y left, +Z up**.

The current values (`0.30, ±0.28, 0.50` m, no rotation) are **placeholders**. Measure the real mounting positions and angles; wrong transforms produce plausible-looking but biased poses.

Positive pitch about Y tilts a forward-facing camera downward; yaw rotates it left/right.

### Filtering and trust

- `maxAmbiguity = 0.3` (single-tag observations only)
- `maxZError = 0.75 m`
- `linearStdDevBaseline = 0.08 m`, `angularStdDevBaseline = 0.06 rad`
- `cameraStdDevFactors = {1.0, 1.0}`
- MegaTag 2 factors: linear `0.5`, angular `∞` (rotation ignored)

Observations outside field bounds or with no tags are rejected.

### Timestamps

PhotonVision timestamps are in the FPGA timebase. `Vision` passes them through unchanged; `CommandSwerveDrivetrain.addVisionMeasurement` applies `Utils.fpgaToCurrentTime(...)` exactly once. Do not convert them in `Vision`, or measurements will land at the wrong time.

### Logging keys

Vision poses are published to NetworkTables under:

- `Vision/<camera name>/TagPoses`
- `Vision/<camera name>/RobotPoses`
- `Vision/<camera name>/RobotPosesAccepted`
- `Vision/<camera name>/RobotPosesRejected`
- `Vision/Summary/...`

Disconnected cameras raise a WPILib warning `Alert`.

## Configuration files

Key files and what to edit:

| File | What it controls |
|---|---|
| `src/main/java/frc/robot/generated/TunerConstants.java` | **Generated by Tuner X** — CAN IDs, bus, encoder offsets, gear ratios, module positions, PID/FF gains, Pigeon ID. Regenerating overwrites hand edits. |
| `src/main/java/frc/robot/subsystems/vision/VisionConstants.java` | Camera names, robot-to-camera transforms, filtering, trust factors |
| `src/main/deploy/pathplanner/settings.json` | Robot width/length, mass, MOI, trackwidth, module positions, drive gearing, max speed |
| `src/main/deploy/pathplanner/autos/*.auto` | Autonomous routines (edit in PathPlanner GUI) |
| `src/main/deploy/pathplanner/paths/*.path` | Path geometry (edit in PathPlanner GUI) |
| `.wpilib/wpilib_preferences.json` | Project year and team number |
| `build.gradle` | GradleRIO version, Java 17, simulation GUI/DS, test config |

**Keep `settings.json` and `TunerConstants.java` geometry consistent.** `TunerConstants` uses module positions of `±10.25 in` (≈ `0.260 m`), while `settings.json` currently lists `±0.273 m`. A mismatch degrades PathPlanner tracking accuracy.

`frcStaticFileDeploy` uses `deleteOldFiles = false`, so renamed or removed deploy assets linger on the roboRIO. Delete stale files manually if behavior seems out of date.

## Troubleshooting

### Robot builds/sims but drives wrong on real hardware
Check `generated/TunerConstants.java` first: CAN bus name, device IDs, encoder offsets, `kInvertLeftSide` / `kInvertRightSide`, gear ratios, and wheel radius. Regenerating from Tuner X with the correct robot config is usually safer than hand-editing.

### Autos do not mirror for the red alliance
Expected. Mirroring is manual via the **"Manual Mirror Override"** SmartDashboard chooser.

### Autos do not run
Check that `deploy/pathplanner/settings.json` is present and valid; check the Driver Station console for `Failed to configure PathPlanner AutoBuilder`.

### Path tracking is poor when the robot is rotated
See [Path-following output](#path-following-output): `driveRobotRelative` uses a field-centric request for robot-relative speeds.

### Vision does not update the pose
Check, in order:

1. Camera names match `frontleftcamera` / `frontrightcamera` exactly.
2. Cameras are connected (watch the WPILib alerts).
3. AprilTag pipelines are active and tags are in view.
4. `VisionConstants` transforms are measured, not placeholders.
5. Field layout matches the 2026 default field.
6. `Vision` is registered with `CommandScheduler` (it is, in `RobotContainer`).

### Pose has plausible drift or turns stop at the wrong angle
Vision yaw corrections depend on correct camera transforms. Also note `TurnToHeading` currently reads `getState().Pose.getRotation()` (fused gyro + vision). For purely relative turns, the gyro heading (`getState().RawHeading` or `drivetrain.getPigeon2().getRotation2d()`) is more stable and immune to mid-turn vision corrections.

### Deploy succeeds but old files remain
`deleteOldFiles = false` in `build.gradle`. Remove stale assets on the roboRIO (`/home/lvuser/deploy`) manually.

## Known issues and leftovers

- `commands/Autos.java`, `commands/ExampleCommand.java`, `subsystems/ExampleSubsystem.java`, and `Constants.java` are unused WPILib template leftovers.
- `subsystems/vision/VisonConsumer.java` is empty and misspelled; the real `VisionConsumer` interface lives inside `Vision.java`.
- `VisionIOLimelight.java` is unused (no Limelight on the robot).
- `driveRobotRelative(...)` mixes robot-relative speeds with a field-centric request (see above).
- PathPlanner mirroring is manual, not alliance-aware.
- AdvantageKit, ChoreoLib, and PhotonLib are vendordeps. Only PhotonLib is actively used; AK logging and Choreo trajectories are not integrated.
- The vision camera transforms are placeholders until measured.
- `TurnToHeading` has no velocity feedforward and does not clamp its output to the profiled max angular velocity; it can overshoot or hunt, and it silently times out after 5 seconds.
